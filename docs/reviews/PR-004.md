## Scope and existing dispositions

- **Ability data.** Separate parsers preserve published live and requested snapshot schemas, merge current spell/rank/cooldown with localized metadata, and schedule a bounded request after a Build change. Session data established that a legacy action tooltip can describe the wrong game rank. Reborn uses native snapshot text and honest fallbacks. Original spell tooltips still use the original action path. The final tree adds native tooltip freshness and run-boundary checks. Attribution of arbitrary card effects to spells remains limited.
- **Curses and racials.** Run reset watchers avoid different consumers competing for ownership of a single transition. Curse identity, boundary filtering, expiration and recognition are exercised in unit tests and historical replay. Native banners can supply duration or timing context. Unrecognized or untimed effects remain incomplete. Racial cooldown uses the current observed remaining/max values and the run clock, with an explicit zero and no synthetic legacy cooldown. The placement path preserves an occupied key and defers protected changes. A native smoke check should cover a custom binding and a run transition. Account-talent button 7 was intentionally removed because the host had no supported trigger.
- **Encounters.** Native Rift versus time and Endless rows remain independent of portal encounters. Guardian timing uses native remaining seconds with run-clock decay and resynchronizes on lair updates. The shared non-Reborn guardian countdown remains on its original branch. The final tree hides stale Reborn positions for empty lairs and keeps a panel entry for respawn data when present. Missing portal identity or conflicting candidates leave the outcome unresolved.
- **Jewelry and original-game paths.** Instance identifiers keep different pieces separate while disallowing inferred acquisition counts without a distinct instance key. Local owner preference and empty Reborn lists are covered. Character-wide totals stay separate from per-item values. Importing Reborn results into original-client Build List and Run History remains the open PR4-03 boundary. The original client has not been smoke-tested on the candidate.
- **Diagnostics, packaging and privacy.** Recording defaults off, uses dedicated SavedVariables and limits record count and bytes. The helper parses Lua-shaped text as data, checks private destination visibility, and verifies payload/base manifests. Existing authenticated CLI credentials are used by the CLI. Key sanitization does not make a capture safe to publish. The addon ZIP has only the addon directories and license. The separate helper ZIP has two launchers, the PowerShell script, and a README. No raw captures, configuration files, secrets, or build directories appear in the ZIPs. Only the small representative replay fixtures are tracked. The PR #4 package script builds both ZIPs, while its current workflow uploads the addon ZIP. PR #6's prerequisite workflow adds separate helper-artifact and tagged-release attachment coverage.

## Integration and release gates

If PR #4 must land separately, first authorize a narrow correction containing the two P1 fixes and the scoped original-client jewelry guard. Use the existing fixed code as evidence and rerun original-client and merge-tree checks before a history-preserving merge commit. Recompare PR #6 once the new main exists. For a single protected integration, preserve the exact PR #4 head in a reviewed stack and require the P1 fixes and PR4-03 disposition in the final tested tree. Avoid an intermediate main tree with either known P1. Separate approval is required for any branch integration. The final prerequisites and scope are in the [PR #6 report](PR-006.md).

Original-client smoke coverage should include startup with prior SavedVariables, a worn jewelry item in Build List and after saving a run, original action tooltips, unchanged key bindings, and existing boss/guardian tracker behavior. Reborn smoke coverage should include one portal encounter with a unit gap or unrelated boss and one racial check across a transition or reload. New native checks remain provisional pending review. A public release follows the planned post-V1 features and final acceptance.
