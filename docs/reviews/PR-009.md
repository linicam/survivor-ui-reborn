### Native ordering and ownership

- AzerothSurvivors/Core.lua:62-83 dispatches handlers in registration order. Run.lua:359-374 requests sync on World entry and Run.lua:453-469 replaces the run and zone tables. The public API documents zone first, then run state and gear, followed on a finished run by the ending lines. Api.lua:65-81 normalizes stable server run IDs, and Api.lua:233-250 exposes the phase and native summary. AZS_RUN.endless distinguishes an Endless continuation using the same run ID. The legacy AZSEND.endl field can also identify an Endless summary.
- AzerothSurvivors/Units.lua:81-96 replaces AZS_GEAR and AZS_ARMOR. Spoils.lua:787-814 replaces AZS_END_LOOT and AZS_END and labels final loot as preceding its end. Spoils.lua:685-723 checks the terminal phase and offers continuation at victory. A polling addon may first see Endless even though the Campaign summary already ran. The exact ordering of the phase update and summary at the server was not inferred from that UI logic. Both orders were exercised through the production event handlers and watcher.
- RebornCompat copies incoming scalar rows and keeps the latest end observation and the preceding different scope. An end freezes the record's run, phase, and equipment observations before a later World or mode change. RunHistory can settle a formerly bound end after Hub entry or a new run, using the bound rows and summary. Campaign victory and the nested Endless result each settle once. The first end can supersede even an observed provisional snapshot with a newer partial or explicitly empty observation. A repeat matching the outcome and supplied time can fill missing evidence. It preserves complete observations and ignores conflicting outcomes or times.
- A delayed reward sidecar is accepted when followed by a matching native end. The published protocol supplies no standalone correlation ID on jewelry, armor, reward, or end messages. A late sidecar without a follow-up end stays unavailable. A packet that arrives only after another valid scope is established and carries no identities can look like that scope's packet. The addon uses the documented order and does not infer extra server guarantees. Fresh stable IDs and a native run-state event are required for new Reborn settlements. History from earlier versions and the original-client path remain readable. Reborn clients that only send session-local IDs lack this new settlement path.
- Checkpoint predicate callers were Options, RebornAnalysis card/projection/mitigation paths and RebornCompat jewelry. They now operate without a generated-table compatibility guess. RebornAnalysis uses scoped native jewelry for its research diagnostics and checks that the measured Meter response contains the requested run ID. The original inventory flow is isolated. The shipped manifest still excludes the legacy Gear Analyzer and Equipment Simulator. [Official Addon API](https://azreborn.com/guides/addon-api)

## Presentation and data boundaries

The existing worn panel keeps its sizing, positioning, font and rarity-color settings. Each Reborn row displays the icon, item name and compact native effects. Both the worn panel and Run History use the same tooltip renderer for the full localized text, including conditional and special lines. Rows without reliable effect text show an unavailable state. Enhancement counts are omitted because this build has no verified count source. The original-client rank, name, slot and empty-slot options remain available on its inventory panel. Reborn's Options preview uses the same current source as the worn panel.

World entry, exit and a changed run ID invalidate retained equipment globals. The follow-up adds an explicit Campaign and Endless boundary and retains the observed end after that boundary. Historical rows and their schemas remain readable.
