# SurvivorUI Reborn

## Development delivery and independent review

- This workflow applies only to SurvivorUI Reborn, including the current Gear & Difficulty Analyzer task. Communicate with the user in Simplified Chinese. Write developer documentation and code comments in English, following existing game localization conventions.
- For each task, inspect repository state and applicable instructions, implement the approved requirements, and run relevant tests, regression checks, and validation. Self-review correctness, product requirements, UX, performance, compatibility, and maintainability. Fix material findings and update relevant developer documentation.
- Review staged changes for scope and sensitive content before committing. Create or use an appropriate development branch, commit task changes, and push to GitHub at meaningful task or milestone boundaries. Create a Draft PR or update the relevant existing PR, reusing it for fixes to the same task. Branch creation, development commits and pushes, Draft PR creation, relevant PR updates, CI execution and inspection, and local test builds and validation are authorized without separate approval.
- Obtain separate explicit authorization before pushing to `main` or another protected production branch, force-pushing or rewriting published history, discarding unrelated user changes, merging a PR or enabling auto-merge, creating release tags or publishing releases, or changing the user's installed addon files. Other publication still requires approval. Keep private diagnostic captures, credentials, personal information, private development notes, and unrelated local files out of published changes and artifacts unless separately authorized.
- Hand off the pushed source and PR for independent review arranged by the user. Self-review and passing tests are inputs to review. Final acceptance remains pending. Verify the reported remote revision and keep the PR and delivery report aligned with it. Identify unpublished changes explicitly and explain any difference between the local build and the pushed commit.
- Keep the existing structured delivery report and include repository, development branch, PR URL, exact remote and local commit SHAs, working-tree cleanliness, and whether the SHAs match. Include changed files, key decisions, implementation status and reliability, omitted or partial requirements, limitations and unresolved defects, automated test results, available CI status, build artifact location and source commit, and actual in-game verification status.
- Before proposing in-game checks, exhaust applicable automation, reuse historical captures and replays, and inspect available native game data and supported API implementations. In a provisional checklist, distinguish confirmed behavior, behavior verified only by automation, behavior supported by source evidence awaiting runtime confirmation, behavior requiring in-game verification, and missing or unsupported runtime capabilities. For each proposed check, give the exact uncertainty, minimum action, expected result, and useful diagnostic evidence. Group checks into as few game sessions as practical. Determine the final manual scope after independent review.

## Implementation and validation

- Use `REBORN_COMPATIBILITY.md` for Reborn API contracts and runtime validation. Confirm the current PR and branch before choosing a baseline. The November 2026 audit started at PR #4 head `b09b1ce`.
- `RebornCompat.lua` owns Reborn API normalization, run identity, cache resets, and diagnostics hooks. `BuildList.lua`, `AbilityTooltip.lua`, `CharacterPane.lua`, and `RunHistory.lua` consume those observations. `Jewelry.lua` and `JewelryData.lua` cover the persistent codex and original-game metadata. Keep source provenance and units explicit in each consumer.
- `Tracker.lua`, `Dial.lua`, `BossBars.lua`, `Guardians.lua`, `Affixes.lua`, and `Effects.lua` handle timing, encounter state, and effects. `WorldMarks.lua` and `SurvivorPlates.lua` rely on frame-synchronous projection. `Meter.lua` and `MeterNow.lua` own meter presentation. Use `/sui perf` to measure a comparable workload before claiming a rendering improvement.
- Keep Reborn behavior gated and preserve the original-game paths and existing configuration keys. Treat unreceived snapshots, known empty snapshots, missing fields, and stale run data according to their individual contracts. Read replacement globals at use time, and prefer stable keys to localized labels for identity.
- Support both English (`enUS`) and Simplified Chinese (`zhCN`) in every change. Localize new or updated player-facing text in both languages, preserve format placeholders, and verify locale-sensitive behavior in both clients or record which in-game checks remain pending.
- Validate with Lua 5.1 and the CI Lua version. Run `lua tests/test_reborn_compat.lua`, `python3 scripts/validate_addon.py`, and `bash scripts/package.sh`. Where available on the branch, run `lua tests/replay_runner.lua <fixture>` for each fixture and, on Windows, the PowerShell tests in `tests`. Validate the built ZIP with `python3 scripts/validate_addon.py --zip <archive>`.
- Keep raw captures, extracted game data, reference addons, and build output outside the production checkout. Run the package script in an isolated source snapshot when output must stay outside the checkout. Convert diagnosis exports with `scripts/replay_session.py`. Commit only small, sanitized fixtures with explicit expectations.
- Real gameplay, native HUD behavior, and frame-time claims require in-game evidence. Keep build stamps with captures.
